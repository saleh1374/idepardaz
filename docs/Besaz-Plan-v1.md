# طرح جامع پلتفرم «ایده ← محصول فیزیکی»

> **نام موقت:** بساز / Besaz — **نسخه سند:** 1.0
>
> **راهنمای برچسب‌ها:**
> `PLACEHOLDER` = عدد یا اطلاعات نیازمند تحقیق بازار
> `NEEDS ENGINEERING REVIEW` = ادعای فنی که قبل از انتشار باید مهندس تأیید کند
> `Integration Pending` = Adapter طراحی می‌شود ولی اتصال واقعی هنوز برقرار نیست

---

## بخش ۱: خلاصه اجرایی و بازتعریف محصول

**بازتعریف یک‌جمله‌ای:**
«بساز» یک **کامپایلر ایده برای دنیای فیزیکی** است: کاربر خواسته‌اش را به زبان انسانی می‌گوید، سیستم آن را به یک **پروژهٔ قابل ساخت** کامپایل می‌کند — Recipe تأییدشده، BOM با قیمت زندهٔ فروشگاه‌های ایرانی، آموزش گام‌به‌گام — و دو خروجی ممکن می‌دهد: «خودم می‌سازم» یا «بسپار به صنعتگر».

**مدل ذهنی — چرا پلتفرم است، نه سایت:**

| سایت تک‌سویه | پلتفرم |
|---|---|
| محتوا → خواننده | ۴ گروه همزمان ارزش می‌گیرند **و** تولید می‌کنند |
| یک منبع درآمد | ۶ جریان درآمد لایه‌ای |
| دادهٔ یک‌طرفه | Data Flywheel دوطرفه |

**چرخهٔ داده (موتور پلتفرم):**
کاربر → پروژه → دادهٔ ساخت واقعی (چه قطعه‌ای واقعاً مصرف شد، کجا خطا کرد، چه جایگزینی جواب داد) → بهبود Recipe و BOM → پیشنهاد بهتر → کاربر بیشتر. این حلقه همان چیزی است که کپی‌کننده نمی‌تواند بخرد: **دادهٔ ساخت واقعی.**

**چشم‌انداز ۵ ساله:** هر وسیله‌ای که یک کاربر معمولی ایرانی بتواند در خانه بسازد، مسیر استانداردش از اینجا بگذرد. ۵۰۰+ Recipe تأییدشده، شبکه ۵۰۰ صنعتگر فعال، و دیتابیس قطعاتی که به «Octopart ایران» تبدیل شود.

**مأموریت:** فاصلهٔ بین «فکر می‌کنم» و «دارمش» را از هفته‌ها سرگردانی به چند ساعت کاهش بده.

**USP چهار ستونی:**
1. **حلقهٔ کامل** — تنها جایی که «ایده تا جسم» در یک محصول بسته می‌شود.
2. **BOM زندهٔ ایران** — قیمت و موجودی واقعی، نه مثال‌های خیالی اینترنت.
3. **ایمنی مهندسی‌شده** — Recipeهای بازبینی‌شده، نه خروجی خام AI.
4. **دو مسیر خروج** — DIY یا سفارش ساخت؛ هیچ رقیبی هر دو را ندارد.

## بخش ۲: تحلیل عمیق مسئله و بازار

### درد هر گروه

| گروه | درد اصلی | وضعیت فعلی |
|---|---|---|
| کاربر عادی/DIY | آموزش ویدئویی هست، ولی نمی‌داند قطعه را از کجا، با چه قیمتی و چگونه سازگار بخرد | یا پول آپاراتِ قطعه‌فرسا می‌شود، یا رها می‌کند |
| صنعتگر | مشتری و اعتماد؛ هزینهٔ جذب مشتری بالا | کارلنسر عمومی است، نه تخصصی ساخت |
| فروشگاه قطعات | ترافیک هدفمند؛ بازاریابی گران | در «لحظهٔ تصمیم خرید» کاربر حضور ندارد |
| طراح Recipe | راه درآمد از دانش ندارد | Instructables حتی پول نمی‌دهد |

### چرا راه‌حل‌های موجود کافی نیستند

- **آپارات/یوتیوب:** ویدئو بدون سبد خرید، بدون قیمت، بدون به‌روزرسانی.
- **فروشگاه‌ها (ECA، روبوایران، کافه‌ربات، آرا الکترونیک افزار):** قطعه بدون مسیر؛ کاربر تازه‌کار چیزی برای جمع‌کردن ندارد.
- **AI عمومی (ChatGPT/Gemini):** BOM خیالی با قیمت غلط و قطعات ناموجود، و برای باتری لیتیومی خطرناک.
- **فریلنسری عمومی:** گران، غیرشفاف، بدون استاندارد ایمنی.
- **دیجی‌کالا:** فقط کالای آماده؛ «ساخت» در واژگانش وجود ندارد.

### اندازه بازار

| بازار | برآورد | وضعیت |
|---|---|---|
| ایران — خردفروشی قطعات الکترونیک | چند صد میلیارد تومان در سال | `PLACEHOLDER` — نیاز به تحقیق میدانی |
| ایران — جامعهٔ فعال Maker (انجمن‌ها، گروه‌ها، دانشگاه‌ها) | ده‌ها هزار کاربر | `PLACEHOLDER` |
| جهان — DIY electronics / maker (قطعه، کیت، ابزار، آموزش) | ده‌ها میلیارد دلار در سال | `NEEDS VALIDATION` |

### روندهای کلیدی

1. **Right to Repair** — قوانین اتحادیه اروپا و چند ایالت آمریکا از ۲۰۲۴+ تعمیرپذیری را الزامی کرده.
2. **گرانی واردات در ایران** — کالای آماده هر سال گران‌تر می‌شود؛ ساخت خودتَن گزینهٔ اقتصادی جدی می‌شود.
3. **AI مانع دانش را برداشته** — تازه‌کار می‌تواند حرف بزند و فهمیده شود.
4. **تولید توزیع‌شده** — سفارش PCB آنلاین (JLCPCB و مشابه) ثابت کرده «تولید کوچک توسط افراد» مقیاس‌پذیر است.

**چرا الان؟** سه موج همزمان (AI، گرانی، Right to Repair) + هیچ بازیگر ایرانی AI و قطعه را ترکیب نکرده. پنجرهٔ ۱۲–۱۸ ماهه.

## بخش ۳: رقبا و نمونه‌های موفق

### ایرانی

| رقیب | وضعیت | شکاف |
|---|---|---|
| **ECA** (eshop.eca.ir) | فروشگاه + انجمن + مقاله | «کاربر می‌گوید چه می‌خواهد بسازد → سیستم BOM می‌سازد» ندارد |

## بخش ۴: معماری محصول — ۷ لایه

```
USER → AI INTENT → RECIPE → BOM → SUPPLIER → BUILD/MAKER → COMMUNITY
```

| # | لایه | وظیفه | ورودی | خروجی | وابسته به | KPI لایه |
|---|---|---|---|---|---|---|
| 1 | **User** | ابراز نیاز به زبان طبیعی | جملهٔ فارسی | درخواست خام | — | نرخ تکمیل ویزارد |
| 2 | **AI Intent** | استخراج نیازمندی‌ها، سؤال تکمیلی، انتخاب Recipe | درخواست خام | `{intent, requirements, missingRequirements, recommendedRecipeId, confidence, warnings}` | Recipes | دقت تطبیق ≥ ۸۰٪ |
| 3 | **Recipe Engine** | قالب‌های تأییدشدهٔ پارامتری | recipeId + پارامترها | RecipeVersion lock شده | Components | تعداد Recipe تأییدشده |
| 4 | **BOM Engine** | تولید لیست قطعات + جایگزین + ruleهای سازگاری | RecipeVersion + params | BOM معتبر | Recipe, Components | نرخ BOM بدون خطا |
| 5 | **Supplier Engine** | قیمت/موجودی زنده، چند تأمین‌کننده، history | BOM | سبد قیمت‌گذاری‌شده | Suppliers | دقت موجودی |
| 6 | **Build / Maker** | دو مسیر: DIY یا سفارش ساخت | سبد + انتخاب | سفارش قطعه یا Quote صنعتگر | BOM, Suppliers, Makers | نرخ تبدیل به خرید |
| 7 | **Community** | پروژه‌های عمومی، نقد Recipe، پرسش‌وپاسخ | پروژهٔ کامل‌شده | محتوا + داده | Projects | پروژه Published/ماه |

**قرارداد بین لایه‌ها:** هر لایه فقط با همسایه‌هایش API مشخص دارد. AI (لایه ۲) **هرگز** مستقیم به دیتابیس قیمت دست نمی‌زند — همیشه از Supplier Engine می‌پرسد.

## بخش ۵: هسته محصول — Recipe Engine

Schema استاندارد (JSON) — پیاده‌سازی رسمی: `docs/recipe.schema.json` و `src/Besaz.Api/Modules/Recipes/RecipePayload.cs`.

### وضعیت‌ها و قانون طلایی

```
Draft → UnderReview → Approved ─┬→ Deprecated → Archived
                        └→ Rejected → Draft (بازگشت با نظرات)
```

- **قانون ۱:** هیچ Recipe بدون نسخه ذخیره نمی‌شود. RecipeVersion **غیرقابل تغییر** است.
- **قانون ۲:** هر Project به یک RecipeVersion دقیق lock می‌شود (`PB-001@1.2.0`).
- **قانون ۳:** تأیید Recipe در سطح HIGH/CRITICAL دو بازبین می‌خواهد: یک فنی، یک ایمنی.
- **اشتقاق (Fork):** طراحان می‌توانند نسخهٔ مشتق بسازند؛ مرجع منبع نگه‌داری می‌شود.
- **Deprecated خودکار:** وقتی قطعهٔ حیاتی از همهٔ تأمین‌کنندگان OutOfStock شد، Recipe Flag می‌شود.

## بخش ۶: BOM Engine و دیتابیس قطعات

```
LogicalPart (مثلاً «سلول 18650»)
   ├── SupplierProduct → Supplier A  (SKU, MPN, Price, Stock, URL)
   ├── SupplierProduct → Supplier B
   └── ComponentSpecification (ولتاژ، جریان، ابعاد، Package، ...)
```

- **PriceHistory:** قیمت هر SupplierProduct با timestamp و منبع.
- **StockStatus:** `InStock / LowStock / OutOfStock / Unknown` + lastSync. Job پس‌زمینه (Hangfire) sync می‌کند.
- **BOM Snapshot:** قیمتِ لحظهٔ ثبت سفارش جدا از قیمت جاری ذخیره می‌شود.
- **BOMItem:** `Required / Optional / Alternative` + qty (می‌تواند فرمول پارامتری باشد).
- **Compatibility Engine** — ruleهای ذخیره‌شده به‌صورت دیتا؛ BOM نامعتبر **اصلاً ساخته نمی‌شود**.

## بخش ۷: AI Engine — دستیار، نه مرجع ایمنی

۴ قابلیت: **Understand / Recommend / Compose / Support** (۱۳ وظیفه → جدول در سند اصلی — پیاده‌سازی: `src/Besaz.Api/Modules/Ai`).

- **RAG:** embedding از Recipeها و LogicalPartها در pgvector؛ AI فقط از زمینهٔ بازیابی‌شده جواب می‌دهد.
- **Structured Output:** خروجی الزاماً JSON مشخص (intent/requirements/recommendedRecipeId/confidence/warnings).
- **Tool-call-only داده:** قیمت، موجودی و جایگزین همیشه با فراخوانی Supplier Engine.
- **قراردادهای ممنوعه (system-level):** بدون Recipe تأییدشده، AI اجازهٔ BOM باتری لیتیومی/برق شهر/پرقدرت ندارد.
- **هزینهٔ MVP:** Provider سازگار OpenAI (اولین adapter: xKiro — `Integration Pending`). در dev از StubProvider قطعی استفاده می‌شود.

## بخش ۸: Safety System — دروازهٔ ایمنی اجباری

| سطح | مثال | الزامات |
|---|---|---|
| LOW | چراغ LED USB، فن USB، پروژه‌های Arduino 5V | هشدار متنی |
| MEDIUM | مدارهای ۱۲ ولت، موتورهای کوچک | هشدار + چک‌لیست |
| HIGH | باتری لیتیومی، پاوربانک | هشدار + تأیید اجباری + Expert Review + چک‌لیست کامل + سن ۱۸+ |
| CRITICAL | برق شهر، سیستم‌های پرقدرت | **در MVP ارائه نمی‌شود — قانون ثابت** |

**Safety Gate (جریان اجباری برای HIGH+):** صفحه هشدار → تأییدیهٔ کاربر (چک‌باکس‌های جدا) → Unlock مراحل + چک‌لیست ایمنی → لاگ AuditLog.

**اصل:** مسئولیت مهندسیِ ایمنی روی Recipe تأییدشده است، نه روی خروجی AI.

## بخش ۱۱: Project به عنوان Asset

## بخش ۱۲: معماری فنی

**الگو: Modular Monolith** — پیاده‌سازی: `src/Besaz.Api` با ماژول‌های `Modules/*` و `Shared`.

**قانون وابستگی:** `Identity ← همه`؛ `AI ← Recipes/Components/Suppliers (فقط interface)`؛ `Community ← Projects ← Recipes ← Components`؛ هیچ وابستگی چرخه‌ای.

**استک:** ASP.NET Core 9 + EF Core + PostgreSQL (JSONB + FTS + pgvector — همه در یک DB)، Redis (فاز بالاتر)، Hangfire (فاز ۳+)، Serilog، React + TS + Tailwind، xUnit + FluentAssertions + Playwright (فاز ۳+).

## بخش ۱۳: دیتابیس — Entityهای کلیدی

```
User 1─n Project n─1 RecipeVersion(locked)
Recipe 1─n RecipeVersion 1─n RecipeComponent n─1 LogicalPart
LogicalPart 1─n ComponentSpecification / ComponentAlternative
LogicalPart 1─n SupplierProduct n─1 Supplier ──(PriceHistory 1─n)──
BOM n─1 RecipeVersion ; BOM 1─n BOMItem n─1 SupplierProduct(snapshot)
Cart 1─n CartItem ; Order 1─n OrderItem ; Order 1─1 Payment 1─n PaymentTransaction
MakerProfile 1─n MakerService ; MakerRequest n─1 Project ; MakerQuote n─1 MakerRequest
AIConversation 1─n AIMessage ; AIRecommendation n─1 RecipeVersion
SafetyApproval / ContentApproval n─1 RecipeVersion ; AuditLog (append-only)
```

ایندکس‌ها: `SupplierProduct(SKU)`, `SupplierProduct(MPN)`, `LogicalPart(category)`, `RecipeVersion(status)`, `PriceHistory(supplierProductId, capturedAt DESC)`, `Project(userId, status)`.

قیمت در OrderItem همیشه snapshot؛ RecipeVersion immutable؛ حذف فیزیکی Recipe/Order ممنوع؛ RTL و تقویم شمسی فقط لایهٔ نمایش، دیتابیس UTC + Gregorian.

## بخش ۱۴: استراتژی بازار ایران و رشد

**بومی‌سازی فنی:** فارسی RTL، تومان، تقویم شمسی، موبایل 09xx، درگاه پشت `IPaymentGateway` (ZarinPal/IDPay اولین — `Integration Pending`)، FTS فارسی.

**استراتژی تأمین:** ۲–۳ فروشگاه غیرانحصاری (ECA، روبوایران، کافه‌ربات — `Integration Pending`).

**جذب کاربر:** SEO فارسی روی Recipeها ← اینستاگرام/یوتیوب ← انجمن‌ها و تلگرام ← دانشگاه/هنرستان.

**جامعه‌سازی:** چالش ماهانه، Featured Projects، لایک/رتبه.
